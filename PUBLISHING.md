# Publishing ScreenshotApp to GitHub

**What goes up, what stays local, and the one decision you have to make
before the first commit.** Rewritten 2026-08-26 against the tree as it
actually stands — the previous version predated the PP-OCR models,
`testassets/gold/`, and `testassets/retired/`, and its size estimates
("roughly 2 MB") are now wrong by two orders of magnitude.

---

## 0. Read this first — the 225 MB problem

`third_party/ppocr/` holds **213 MB of ONNX models**, and
`third_party/onnxruntime/onnxruntime.dll` is another 11 MB.

| file | size |
|---|---|
| `PP-OCRv6_rec_medium.onnx` | 73.1 MB |
| `PP-OCRv6_det_medium.onnx` | 59.2 MB |
| `PP-OCRv6_rec_small.onnx` | 20.3 MB |
| `ch_PP-OCRv5_rec_mobile.onnx` | 15.9 MB |
| `ch_PP-OCRv4_rec_infer.onnx` | 10.4 MB |
| `PP-OCRv6_det_small.onnx` | 9.5 MB |
| `en_PP-OCRv5_rec_mobile.onnx` | 7.5 MB |
| `en_PP-OCRv4_rec_mobile.onnx` | 7.3 MB |
| `ch_PP-OCRv5_det_mobile.onnx` | 4.6 MB |
| `ch_PP-OCRv4_det_infer.onnx` | 4.5 MB |
| `onnxruntime.dll` | 11.0 MB |

Nothing here breaks GitHub's hard 100 MB per-file limit, but **two files are
over the 50 MB threshold where GitHub warns**, and a git repository never
forgets: once these are committed they are in the history permanently, and
every future `git clone` pulls all 225 MB even if you delete them later.

**Recommended: do not commit the models or the DLL.** Pick one:

- **A — Release attachment (recommended).** Zip `third_party/ppocr/*.onnx`
  plus `onnxruntime.dll` and attach it to a GitHub Release. `README.md` tells
  people to unzip it into `third_party/`. Keeps the repo ~8 MB and the
  history clean.
- **B — Download script.** A small script fetching the models from their
  upstream sources; `third_party/ppocr/README.md` already documents the
  provenance (RapidOCR / PaddlePaddle, Apache-2.0) and the ONNX conversions
  are publicly available.
- **C — Git LFS.** Works, but LFS bandwidth on a free account is 1 GB/month
  and a handful of clones exhausts it.

The app degrades gracefully without them: `PpOcr::EnsureLoaded` fails, and
`TextOcr` falls back to `Windows.Media.Ocr`. So a clone with no models still
builds and still runs — it just uses the weaker engine. Say that in the
README so nobody thinks the build is broken.

If you decide to commit them anyway, that is a legitimate choice for a
personal project — just do it knowingly, and add nothing else large later.

## 1. What goes up

| path | why |
|---|---|
| `src/`, `include/`, `tests/`, `tools/` | the actual program (~900 KB) |
| `CMakeLists.txt` | the build |
| `resources/` | **not optional** — `app.rc` embeds the `.ico`, `manifest.xml` and all five PNGs directly into the exe. A missing file here is a build failure, not a missing icon |
| `third_party/json.hpp`, `third_party/pdfgen.[ch]` | vendored deliberately; there is no package manager in this build |
| `third_party/ppocr/README.md` | model provenance and licensing — keep even if the models themselves stay out |
| `.gitignore`, `.gitattributes` | the tree has mixed CRLF/LF; without `.gitattributes` your first commit after any edit shows whole files as changed |
| `HANDOFF.md` | the project's memory. Read §16 before anything else |
| `Plan.md` | original design; out of date in three places, see the top of HANDOFF |
| `PUBLISHING.md` | this file |
| `testassets/` | **your call — see §3** |
| `attic/` | old superseded sources. Harmless, ~139 KB. Drop it if you want a tidy repo |

## 2. What does NOT go up

| path | why |
|---|---|
| `build/` | 27 MB of generated output. `CMakeCache.txt` hard-codes the source directory **and** the toolchain paths of whichever machine configured it — committing it actively breaks the build for everyone else, including future-you on the next PC |
| `ocrprobe.obj` | stray object file from a manual compile |
| `last context.txt` | session scratch notes |
| `consult_ans.txt` | 68 KB of raw consult transcript |
| `testassets/*/out/` | probe output, regenerated by every `OcrProbe score` run |
| `.claude/settings.local.json` | personal permission allowlist |
| `*.log`, `*.pdf`, `Screenshots_*.png` | stray run artefacts |
| the built `.exe` | goes in a **Release**, not the repo. Committed binaries are permanent |

`.gitignore` already covers `build/`, `out/`, `*.log`, the VS per-user state
and the local settings. **Add these before the first commit:**

```gitignore
# --- Stray build/scratch artefacts --------------------------------------------
*.obj
last context.txt
consult_ans.txt

# --- Large model blobs (see PUBLISHING.md §0) ---------------------------------
# Remove these three lines if you chose to commit the models.
third_party/ppocr/*.onnx
third_party/onnxruntime/onnxruntime.dll
```

## 3. Privacy review — do this before pushing, not after

This repo contains **your own screenshots and your own machine's paths**.
None of it is catastrophic, but a push is permanent, so spend five minutes:

1. **`testassets/` is 5 MB of real screen captures.** Mostly web pages, docs
   and code, but they are *your screen*: `Screenshot_2026-08-10_16-53-43.png`
   shows a filesystem path `D:\coding\screenshotc++`, and
   `Terminal_2026-08-26_dense-dark.png` is a full capture of a development
   session. One capture was already deleted mid-project for containing
   personal information (`Scrollshot_2026-08-10_11-05-23`). **Look through
   `testassets/captures/`, `testassets/gold/` and `testassets/retired/`
   yourself before deciding.**
   - Keeping them makes the benchmark reproducible, which is most of what
     makes this project interesting to anyone else.
   - If you would rather not, exclude `testassets/` entirely and note in the
     README that the corpus is local. Nothing in the build depends on it —
     only `OcrProbe` reads it.
2. **`HANDOFF.md` and `PUBLISHING.md` contain `C:\Users\abdul\...` paths** in
   several places (the log location, the scratch directories). That exposes
   your Windows username. Harmless to most people; a search-and-replace to
   `%APPDATA%` / `<user>` takes a minute if you care.
3. **`testassets/truth/*.gt.txt`** are transcriptions of those screenshots —
   same review applies.

## 4. Two things missing that GitHub expects

1. **There is no `LICENSE`.** GitHub renders a repo without one as "all
   rights reserved" — nobody may legally use it. MIT is the usual choice for
   something like this.
2. **No `THIRD_PARTY_NOTICES.md`.** Not strictly required — `json.hpp` (MIT)
   and PDFGen (public domain) carry their licence text in their own headers,
   and `third_party/ppocr/README.md` records the model provenance
   (RapidOCR and PaddleOCR, both Apache-2.0; onnxruntime, MIT) — but a single
   notices file is the norm and takes ten minutes.
3. While you are there: `resources/icons/*.png` — if those came from an icon
   set rather than your own hand, check its licence.

## 5. Creating the repo and verifying before you commit

```bash
cd /path/to/screenshotc++
git init
git add -A
```

> **Expect this on a copied project tree**, because the folder still carries
> the *other* PC's owner SID:
>
> ```
> fatal: detected dubious ownership in repository at 'E:/code/screenshotc++'
> ```
>
> It is a safety check, not corruption. Either take ownership of the folder in
> Windows, or tell git the directory is fine:
>
> ```bash
> git config --global --add safe.directory E:/code/screenshotc++
> ```
>
> (Verified on this machine: the tree copied from the previous PC triggers it
> on the very first `git ls-files`.)

**Now stop and check what you are about to commit.** This is the step that
catches a broken `.gitignore` before it becomes history:

```bash
# Verified on 2026-08-26 with the .gitignore additions above in place:
#   186 files, 4.31 MiB - src/, include/, tests/, tools/, resources/,
#   third_party/ (sources only), testassets/, attic/, CMakeLists.txt, the
#   dotfiles and the .md files. Roughly 110 of the 186 are testassets.
git status --short

# Must print NOTHING. Anything here means build/ is being tracked.
git ls-files build | head

# Must print NOTHING if you took option A or B in §0.
git ls-files "*.onnx" "*.dll"

# Must print NOTHING - stray artefacts and regenerated probe output.
git ls-files "*.obj" "last context.txt" consult_ans.txt "testassets/*/out/*"

# Sanity-check the total. Measured: 4.31 MiB with testassets included and
# the models excluded. Under 1 MiB if you also drop testassets/ and attic/.
# ~230 MB if the models went in - that is the number to watch for.
git count-objects -vH
```

Only when those four look right:

```bash
git commit -m "Initial commit: ScreenshotApp"
```

## 6. Pushing

**GitHub CLI** — creates the repo and pushes in one command:

```bash
gh repo create screenshotc++ --private --source=. --remote=origin --push
```

**Plain git** — create the repo on github.com first, and **do not tick "Add a
README"**; an initialised remote makes the first push get rejected:

```bash
git remote add origin https://github.com/<you>/screenshotc++.git
git branch -M main
git push -u origin main
```

If you did tick it: `git pull --rebase origin main` then push.

## 7. Shipping the exe and the models

```bash
gh release create v1.0.0 \
  build/Release/ScreenshotApp.exe \
  ppocr-models.zip \
  --title "ScreenshotApp v1.0.0" \
  --notes "Windows x64. Unzip ppocr-models.zip into third_party/ for the PP-OCR engine; without it the app falls back to Windows.Media.Ocr."
```

## 8. README essentials

Whatever else it says, it must cover:

- **What it is** — a Windows screenshot tool whose interesting part is the OCR
  text extraction (PP-OCRv6 through onnxruntime, with `Windows.Media.Ocr` as
  a fallback).
- **The models are a separate download** and the app works without them.
- **Build**: VS 2022 (Community *or* BuildTools) + the Windows SDK, then
  `cmake -S . -B build -G "Visual Studio 17 2022" -A x64` and
  `cmake --build build --config Release`. **Do not** copy the
  `-DCMAKE_SYSTEM_VERSION=10.0.26100.0` flag out of HANDOFF §16.3 — that pins
  one machine's exact SDK and will fail on anyone else's.
- **Accuracy numbers, with their caveats** — 97.9% on the tuning corpus,
  92.5% on a held-out set, ~1.9 s per capture. Say which corpus is which;
  HANDOFF §16.1 explains why the held-out figure is the honest one.

## 9. Afterwards

The first thing to verify on a fresh clone, on any machine:

```bash
cmake -S . -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release
cd build && ctest -C Release --output-on-failure    # expect 124 tests green
```

If that fails on a clean clone, something in this document is wrong — fix the
document, not just your local copy.
